TYPED COLLECTION GENERICS
  𝕃[T]            Ordered list where all elements are type T
  𝕃[𝕊]            List of strings
  𝕃[𝕄[𝕊:𝕀]]      List of string→integer maps
  𝕄[K:V]          Map with key type K and value type V
  𝕄[𝕊:𝔹]          Map of string keys to boolean values
  𝕄[𝕊:𝔻]          Map of string keys to any-type values

  Unparameterized 𝕃 and 𝕄 remain valid (equivalent to 𝕃[𝔻], 𝕄[𝔻:𝔻]).
  At JOIN points in pipelines, typed collections enforce narrowing (see
  Section 22 and Section 31).

RETURN TYPE WITH QUALIFIER
  A typed collection may carry a return qualifier using the form TYPE:QUAL.
  𝕃[𝕊]:CLI     = ordered list of CLI script strings
  𝕄[𝕊:𝔻]:JSON  = JSON map with string keys and dynamic values
  The qualifier follows the outermost type bracket and is a plain label.
  Valid qualifiers mirror those in Section 26: CLI · MODULE · JSON · STEPS.

TYPE INFERENCE SYNTAX
  𝕋 alone means "infer from context"
  𝕋→𝕊 means "infer, expected to resolve to string"
  𝕌[𝕊|𝕀] means "string or integer"
  Receiver resolves inference before executing; NAK[1] if unresolvable.
  Cycle detection rule: see Section 22.

SECTION 7 — TENSE MARKERS
────────────────────────────────────────────────────────────────────────────────
τ⁻          TENSE:PAST              Past tense
τ⁰          TENSE:PRESENT           Present / now
τ⁺          TENSE:FUTURE            Future / projected
τ∞          TENSE:ETERNAL           Timeless / always true
τ↺          TENSE:RECURRENT         Recurring / habitual
              Syntactically distinct from CTRL:LOOP (↺ alone) by the
              required τ prefix. Parsers MUST check for τ before ↺.

TENSE NEGATION
  Prefix ¬ to any tense marker to express its negation:
  ¬τ⁻        Not in the past / not yet historical
  ¬τ⁺        Not in the future / will not occur
  ¬τ∞        Not universally true / contextually bounded
  ¬τ↺        Non-recurring / one-time

  Rule: ¬τ attaches to the tense marker only, not to the clause.
  To negate the entire clause, wrap: ¬⌈ CLAUSE ⌉.
  Example: ¬τ⁺ ※ «EVENT» = this event will not occur
           ¬⌈ τ⁺ ※ «EVENT» ⌉ = the claim "event will occur" is false

RELATIVE TENSE
  τ[+N]      N turns/steps from now (N is 𝕀)
  τ[-N]      N turns/steps ago
  τ[>REF]    After reference point REF
  τ[<REF]    Before reference point REF
  τ[=REF]    At reference point REF (simultaneous with)

  REF may be: a session variable ⟪σ:NAME⟫, a named event, or an integer
              step count expressed as a plain 𝕀 literal.
  Examples:
    τ[+3]           Three turns from now
    τ[>⟪σ:START⟫]   After the session-stored start event
    τ[<DEPLOY]      Before the deploy event
    ℳ[τ[+5]]        Memory expires 5 turns from now

  Relative tense may be combined with aspect markers:
    τ[+2] · Σ       Still ongoing two turns from now
    τ[+1] · ✔       Completed one turn from now

SECTION 9 — CAUSALITY
────────────────────────────────────────────────────────────────────────────────
⊢           CAUSE:BECAUSE           A causes / is the reason for B
∴           CAUSE:THEREFORE         A therefore B
∵           CAUSE:SINCE             Since A, B follows
⟺           CAUSE:IFF               If and only if (bidirectional implication)
⊥⊢          CAUSE:DESPITE           Despite A, B holds

  NOTE: ⊢ is the sole owner of the logical turnstile glyph in this spec.
  It carries causality semantics exclusively. ⊩ (double turnstile) carries
  derivation semantics exclusively (Section 2). Parsers MUST NOT
  context-guess between them.

OPERATOR PRECEDENCE WITHIN CAUSALITY (high to low)
  1. ⊢   (because — binds tightly to its antecedent)
  2. ∵   (since)
  3. ∴   (therefore)
  4. ⟺   (iff — widest scope; spans both sides equally)
  5. ⊥⊢  (despite)

  Worked example: A ⊢ B ∴ C binds as (A ⊢ B) ∴ C
  — B is the consequence of A; C is therefore derived from that causal pair.

SECTION 12 — SOURCE & ATTRIBUTION
────────────────────────────────────────────────────────────────────────────────
©           SRC:SELF                Derived from own reasoning (transmitting agent)
©⟨AI⟩       SRC:AI_OTHER            Sourced from a different AI agent; content
                                    is relayed, not re-derived independently
©⟨H⟩        SRC:HUMAN               Sourced from a human
©∅          SRC:UNKNOWN             Source unknown / unverified

  MULTI-AGENT ATTRIBUTION RULE
  When an agent relays another agent's output without re-deriving it,
  the transmitter MUST use ©⟨AI⟩ (SRC:AI_OTHER), not © (SRC:SELF).
  If the transmitting agent independently re-derives or synthesizes the
  content, © (SRC:SELF) is correct even if the input came from another agent.
  Attribution chains may be stacked: [©⟨H⟩ · ©⟨AI⟩] = human-sourced,
  relayed by an AI.

SECTION 13 — QUANTIFICATION
────────────────────────────────────────────────────────────────────────────────
∀           QUANT:ALL               Universal / all instances
∃           QUANT:SOME              At least one
∄           QUANT:NONE              None / no instance
∂           QUANT:PARTIAL           A subset / some portion

AGENT QUANTIFICATION
  Quantifiers may scope over agent sets in multi-agent topology expressions.
  Syntax: QUANT[AGENT_SET]

  ∀[⟨AI:*⟩]        All agents in session
  ∃[⟨AI:*⟩]        At least one agent in session
  ∃[𝕀:N][AGENT_SET] At least N agents from the set
  ∀[⟨AI:ROLE⟩]     All agents with a given role

  QUORUM EXPRESSIONS (used with ⊙ JOIN; see Sections 24 and 31)
  ⊙[∃[𝕀:N]]        Join succeeds when at least N agents have responded
  ⊙[∀]             Join requires all forked agents to respond (default)
  ⊙[∃[𝕀:1]]        Any single response is sufficient to proceed

  ¬ACK              Failed-response counting modifier for quorum expressions.
                    ⊙[∃[𝕀:2] · ¬ACK] = quorum of 2 counting NAK responses.
                    Without ¬ACK, only ACK responses count toward quorum.

  Examples:
    ⊙[∃[𝕀:2]]           Two-of-N quorum join (ACK responses only)
    ⊙[∀]                All-must-respond join (strict)
    ⊙[∃[𝕀:1]]           First-responder wins (race join)
    ⊙[∃[𝕀:2] · ¬ACK]    Two responses of any kind (ACK or NAK) count

SECTION 18 — META-COMMUNICATION
────────────────────────────────────────────────────────────────────────────────
Ω           META:SELF_REF           Self-referential statement
∇PECS       META:PROTOCOL           Operating under AICO standard
⊞Ω          META:REQ_CLARIFY        Requesting clarification
⊟Ω          META:OFFER_CLARIFY      Offering clarification
ERR[n]      META:ERROR              Error code n in last transmission
ACK         META:ACK                Acknowledged / received
NAK         META:NAK                Not acknowledged / rejected
NAK[n]      META:NAK_REASON         Rejected, reason code n

NAK REASON CODES
  NAK[1]  = type unresolvable / inference cycle detected
  NAK[2]  = version unsupported
  NAK[3]  = macro undefined or parameter missing without default
  NAK[4]  = validation contract failed (⇒✓{} unsatisfied)
  NAK[5]  = feature unsupported (agent lacks required ∇CAP flag)
  NAK[6]  = resource or quota exceeded
  NAK[7]  = authorization / permission denied
  NAK[8]  = timeout — session expiry notification (sent by session layer)
  NAK[9]  = execution timeout — ∇PECS[TIMEOUT[N]] deadline exceeded
              (sent by receiver when it cannot begin execution within N turns)
  NAK[10] = pipeline stage failure (see Section 31)
  NAK[11] = quorum not met (see Section 31)
  NAK[12] = memory write-lock denied (see Section 25)
  NAK[13] = recursive macro detected (see Section 21)
  NAK[14+]= reserved for future minor-version assignment.
              Agents MUST NOT use NAK[14+] for implementation-specific
              meanings. On receipt of an unknown NAK[n≥14], treat as NAK[5].

  NOTE: NAK[8] and NAK[9] are distinct. NAK[8] is emitted by the session
  layer on session expiry (analogous to ERR[8] in session notifications).
  NAK[9] is emitted by a receiver that cannot begin execution within the
  ∇PECS[TIMEOUT[N]] window declared by the sender. Implementations MUST
  not conflate these.

SECTION 19 — VERSION NEGOTIATION
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Before transmitting, agents handshake to confirm mutual AICO support level.
  Prevents silent misinterpretation of unsupported tokens.

SYNTAX
  ∇[v:4.0]                          Declare AICO-4.0 compliance
  ∇?[v:4.0]                         Query: do you support AICO-4.0?
  ∇ACK[v:4.0]                       Confirm: yes, I support 4.0
  ∇NAK[v:4.0]                       Decline: version not supported
  ∇CAP{...}                         Declare supported feature subset

FEATURE FLAGS (use inside ∇CAP{})
  INFER        Type inference supported
  MACRO        Named macros supported
  SESSION      Session state supported
  STREAM       Streaming / chunked transmission supported
  ASYNC        Async calls supported
  BROADCAST    Multi-agent broadcast supported (includes ACK modes)
  VALIDATE     Pre-transmission validation supported
  MEMORY       Memory scoping supported
  ARITH        Arithmetic operators supported (see Section 30)
  QUORUM       Quorum join expressions supported (see Section 31)
  PIPELINE_ERR Pipeline error propagation supported (see Section 31)
  GENERIC_TYPE Typed collection generics supported (see Section 4)

  Agents MUST NOT use a feature requiring a flag unless that flag was
  confirmed in ∇CAP{} negotiation. Unrecognized flags in a peer's ∇CAP{}
  MUST be silently ignored (forward compatibility).

SECTION 20 — SESSION STATE
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Persistent context across multiple transmissions. Eliminates re-declaring
  ∇PECS, entity context, and shared variables on every message.

SESSION LIFECYCLE
  ⟪OPEN⟫                            Open a new session
  ⟪OPEN:ID⟫                         Open session with explicit ID
  ⟪OPEN:ID · τ[+N]⟫                 Open session with explicit ID and
                                      expiry of N turns from open time.
                                      N is 𝕀. On expiry the session behaves
                                      as if ⟪CLOSE⟫ was received; all agents
                                      in the session receive NAK[8].
  ⟪CLOSE⟫                           Close and flush session
  ⟪RESUME:ID⟫                       Resume a previous session by ID
  ⟪FLUSH[TARGET]⟫                   Clear specified session targets

FLUSH TARGET GRAMMAR
  ⟪FLUSH[σ]⟫          Clear all session variables (⟪σ:*⟫)
  ⟪FLUSH[μ]⟫          Undefine all macros declared in this session
  ⟪FLUSH[ℳ]⟫          Clear all memory slots declared in this session
  ⟪FLUSH[σ · μ]⟫      Clear variables and macros
  ⟪FLUSH[*]⟫          Clear all targets (σ, μ, and ℳ)
  ⟪FLUSH[σ:NAME]⟫     Clear one named session variable
  ⟪FLUSH[μ:NAME]⟫     Undefine one named macro
  ⟪FLUSH[ℳ:NAME]⟫     Clear one named memory slot

  ⟪FLUSH[TARGET]⟫ requires a TARGET argument. Bare ⟪FLUSH⟫ without a
  target is a grammar error → NAK[3].

  FLUSH does NOT close the session. ∇PECS declarations and the session
  ID survive FLUSH. Private scopes ⟮ ⟯ survive unless their owning
  agent explicitly flushes them.

SESSION VARIABLES
  ⟪σ:NAME ← VALUE⟫                  Assign session variable NAME
  ⟪σ:NAME⟫                          Reference session variable NAME
  ⟪σ:*⟫                             All session variables (wildcard)

SCOPE RULES
  ⟪ ⟫    Session scope    — persists until ⟪CLOSE⟫ or expiry
  ⟮ ⟯    Private scope    — visible only to declaring agent
  ⦃ ⦄    Shared scope     — visible to all agents; write-locked to owner

SECTION 21 — NAMED MACROS
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Define reusable token sequences. One macro token replaces N tokens.
  Enables protocol-level compression for repeated patterns.

DEFINITION SYNTAX
  μ:NAME ≡ ⌈ TOKEN_SEQUENCE ⌉       Define macro NAME
  μ:NAME ≡ ⌈ ... ⌉ (®↑)             Define with scope modifier

PARAMETER SYNTAX
  Macros may declare overridable parameters using ⟦PARAM⟧ placeholders
  inside their definition body. Angle-bracket delimiters ⟦ ⟧ are used
  exclusively for macro parameters inside ⌈ ⌉ bodies, making them
  syntactically unambiguous from SET { } and CTRL ⟦?⟧/⟦!⟧.

  DEFINITION WITH PARAMETERS
    μ:NAME ≡ ⌈ λ:WRITE[⟦LANG⟧ · ⟦QUAL⟧ · ⟦DEPTH⟧] ⌉
    Parameters are named identifiers inside ⟦ ⟧ within the macro body.

  CALL WITH OVERRIDE
    μ:NAME[PARAM:VALUE · PARAM:VALUE]
    μ:PYWRITE[LANG:𝕊:"TypeScript" · QUAL:Φ³]
    Unspecified parameters use the definition-time defaults.
    If a parameter has no default and no override is provided → NAK[3].

  PARAMETER DEFAULT SYNTAX
    μ:NAME ≡ ⌈ λ:WRITE[⟦LANG=𝕊:"Python"⟧ · ⟦QUAL=Φ⁴⟧] ⌉
    = LANG defaults to Python, QUAL defaults to production quality.

CALL SYNTAX
  μ:NAME                             Expand macro NAME (no overrides)
  μ:NAME[PARAM:VALUE ...]            Expand with parameter overrides
  ¬μ:NAME                            Undefine macro NAME

MACRO RECURSION RULE
  A macro body MUST NOT reference its own name, directly or transitively.
  Mutual recursion (μ:A references μ:B, μ:B references μ:A) is also
  prohibited. Any recursive reference detected at definition time → NAK[13].
  Receivers MUST validate macro bodies on definition, not at call time.
  Cycle detection algorithm: depth-first traversal of macro reference
  graph; if any node is visited twice → NAK[13].

BUILTIN MACROS (pre-defined)
  μ:INIT    ≡ ⌈ ∇[v:4.0] · ✧ · ⊕ · ΛΣ ⌉
             Standard session open greeting
  μ:ACK+    ≡ ⌈ ACK · ✦ · ⊟Ω ⌉
             Acknowledge and offer clarification
  μ:ERR!    ≡ ⌈ NAK · ↓ε · ⊞Ω ⌉
             Reject and request clarification
  μ:PYWRITE ≡ ⌈ λ:WRITE[⟦LANG=𝕊:"Python"⟧ · ⟦QUAL=Φ⁴⟧ · ⟦DEPTH=Δ+⟧] ⌉
             Parameterized write macro

SECTION 22 — TYPE INFERENCE
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Receiver infers ambiguous types from context. Reduces explicit type
  annotation burden while preserving zero-ambiguity contract.

INFERENCE TOKENS
  𝕋           Infer type from context
  𝕋→TYPE      Infer, expected resolution hint
  𝕌[A|B]      Union — one of listed types
  𝔻           Fully dynamic, any type accepted

INFERENCE RULES (receiver must follow, in order)
  1. Check session variables for prior type declaration of this symbol
  2. Check macro definitions for embedded type
  3. Infer from operator context (e.g. ↺ implies 𝕃 or 𝕄 input)
  4. Infer from sibling parameters in same [ ] block
  5. If still unresolved, apply generic type default: 𝔻
  6. CYCLE DETECTION: if inference of symbol A depends on inference of
     symbol B, which depends on A (directly or via chain), this is a
     circular inference. Do NOT apply Rule 5 as fallback for cycles.
     → NAK[1] with cycle members listed in ERR payload.
     Example of illegal cycle: λ:F[𝕋 · 𝕋] ⇒ 𝕋 where all three 𝕋
     reference each other with no anchoring context.

UNION TYPE NARROWING AT JOIN
  When a pipeline stage produces 𝕌[A|B] and the downstream stage or JOIN
  expects a concrete type, the following rules apply:

  1. IMPLICIT NARROWING: if only one member of the union satisfies the
     downstream type constraint, it is selected automatically.
     𝕌[𝕊|𝕃] flowing into a stage that declares ⇒ 𝕊 → narrowed to 𝕊.

  2. EXPLICIT NARROWING: sender may declare narrowing inline:
     𝕌[𝕊|𝕃]→𝕊    instructs receiver to narrow to 𝕊

  3. AMBIGUOUS NARROWING: if multiple union members satisfy the
     downstream constraint, receiver issues NAK[1] with message:
     «ambiguous union: specify narrowing with 𝕌[...]→TYPE»

  4. TYPED COLLECTION NARROWING: 𝕃[𝔻] accepted where 𝕃[𝕊] expected
     only if all elements at runtime are 𝕊; otherwise NAK[1].
     Agents with GENERIC_TYPE flag enforce this at transmission;
     others treat 𝕃[𝔻] as untyped 𝕃.

SECTION 23 — ERROR CONTRACTS & VALIDATION
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Declare upfront what constitutes a valid response. Receiver self-validates
  before transmitting. Eliminates correction round-trips.

VALIDATION SYNTAX
  ⊞✓{RULES}                         Request must satisfy these rules
  ⇒✓{RULES}                         Response must satisfy these rules

  Rules may be combined inside the same { } block using · as separator.
  Two rule forms exist and may be freely mixed:

  FLAG RULES (𝔹:LABEL)
    𝔹:TYPED      Output must be fully typed
    𝔹:DOCS       Output must include documentation
    𝔹:TEST       Output must include tests

  CONSTRAINT RULES (✓[...])
    ✓[κ¹]             Output must be verified / certain
    ✓[Δ[n]]           Output must meet line count
    ✓[ERR:HANDLE]     Output must handle errors explicitly
    ✓[∄ ERR]          Output must contain no errors

  EXCLUSION RULE
    ✗[PATTERN]        Output must NOT contain pattern

  MIXED EXAMPLE
    ⇒✓{𝔹:TYPED · 𝔹:DOCS · ✓[ERR:HANDLE]}
    = Response must be fully typed, documented, with explicit error handling.

VALIDATION FAILURE BEHAVIOR
  If receiver cannot satisfy ⇒✓{} constraints → NAK[4] before responding.
  If receiver partially satisfies → ACK · ◑ · ⊟Ω[unsatisfied constraints].

SECTION 25 — MEMORY SCOPING
────────────────────────────────────────────────────────────────────────────────
PURPOSE
  Explicit control over what persists, what expires, and what is
  shared vs private. Defines retention policy, not just container.

MEMORY DECLARATIONS
  ℳ⟪NAME⟫                           Declare session-scoped memory slot
  ℳ⟮NAME⟯                           Declare private memory slot
  ℳ⦃NAME⦄                           Declare shared memory slot
  ℳ←VALUE                           Write to memory
  ℳ→                                Read from memory
  ℳ⊘                                Clear memory slot

MEMORY EXPIRY
  ℳ[∞]        Permanent             Never expires
  ℳ[✔]        Session-scoped        Expires on ⟪CLOSE⟫
  ℳ[τ↺]       Turn-scoped           Expires after one exchange
  ℳ[𝕀:N]      N-turn retention      Expires after N exchanges
  ℳ[τ[+N]]    Relative expiry       Expires N turns from declaration
                                    N is 𝕀; uses relative tense (Section 7)

WRITE-LOCK OWNERSHIP
  Owner of a memory slot = the agent that declared it.
  Ownership is implicit when ℳ⦃NAME⦄ is declared without @ qualifier.
  Explicit ownership: ℳ⦃NAME⦄@⟨AI:ID⟩

  Rules:
  1. The declaring agent is the owner. Ownership transfers only via explicit
     reassignment sent by the current owner:
       ℳ⦃NAME⦄@⟨AI:NEW_OWNER⟩ ← VALUE
     If the target agent is offline or absent → NAK[7] (permission denied).
     If the owning agent closes or terminates unexpectedly, the shared
     memory slot becomes write-unlocked (no owner) until re-claimed with
     a new ℳ⦃NAME⦄@⟨AI:ID⟩ declaration by any agent in session.
  2. Non-owners may READ ⦃ ⦄ shared memory freely.
  3. Non-owners attempting to WRITE shared memory → NAK[12].
  4. Private ⟮ ⟯ memory: no other agent may read or write, ever.
  5. Session ⟪ ⟫ memory: readable and writable by all agents in session
     unless a write-lock is applied with @.

INHERITANCE
  Child scopes inherit parent memory unless ⟮ ⟯ (private) is declared.
  ⦃ ⦄ shared memory write-lock is not inherited by child scopes.

SECTION 27 — GRAMMAR RULES

TRANSMISSION STRUCTURE

24. Broadcast thresh.  ⇝?[∃[𝕀:N]] — custom ACK threshold appended to ⇝?

OPERATOR PRECEDENCE (high to low)
  1. ⌈ ⌉  { }  [ ]  ( )  ⟨⟨⟩⟩    Grouping / scope / arithmetic
  2. λ  μ  ℳ                       Definitions
  3. ✓  ✗                           Validation contracts
  4. ⊢  ∴  ∵  ⟺                    Causality (see Section 9 for internal order)
  5. ⊩                              Derivation (Section 2)
  6. →  ↠  ↠!  ↠?  ↠⊘              Transmission / topology / pipeline modes
     ⇝  ⇝!  ⇝?  ⇜
  7. ⊗  ⊙  ⊙[Q]  ⊕                 Fork / join / mesh
  8. ·                               Clause separation

DISAMBIGUATION TABLE
  ≺     CMP:LT (Section 6) vs OP:PRECEDES (Section 2)
        Rule: both operands 𝕀 or 𝔽 → CMP:LT.
              either operand ENTITY or event → OP:PRECEDES.

  ↺     CTRL:LOOP (Section 5) vs TENSE:RECURRENT component of τ↺ (Section 7)

  ¬     BOOL:NOT (Section 6) when preceding a boolean expression;

        Rule: attachment target determines role unambiguously.

SECTION 30 — ARITHMETIC & NUMERIC OPERATORS
════════════════════════════════════════════════════════════════════════════════
PURPOSE
  Express computed numeric values inline. Required for conditional logic
  over numeric state, pipeline step counts, memory expiry arithmetic,
  and loop bounds. Requires ARITH feature flag in ∇CAP{}.

OPERATORS
  +           ARITH:ADD               Addition
  −           ARITH:SUB               Subtraction  (use − U+2212, not ASCII -)
  ×           ARITH:MUL               Multiplication
  ÷           ARITH:DIV               Division
  %           ARITH:MOD               Modulo
  ^           ARITH:POW               Exponentiation

NUMERIC EXPRESSION SYNTAX
  Arithmetic expressions use dedicated delimiters ⟨⟨ ⟩⟩ to avoid any
  ambiguity with other bracket forms (see Section 3).
  Expressions appear inside [ ] parameter blocks or ⌈ ⌉ scope blocks.
  They are always evaluated before the parent expression.

  Syntax: ⟨⟨EXPR⟩⟩ where EXPR is an infix arithmetic expression.
  Examples:
    ⟨⟨𝕀:3 + 𝕀:1⟩⟩           = 4 (integer addition)
    ⟨⟨𝔽:1.5 × 𝔽:2.0⟩⟩       = 3.0
    ⟨⟨⟪σ:N⟫ + 𝕀:1⟩⟩         = session variable N plus 1
    ⟨⟨⟪σ:COUNT⟫ % 𝕀:2⟩⟩     = N mod 2 (even/odd check)

ARITHMETIC IN CONTEXT
  Loop with computed bound:
    ↺[⟨⟨⟪σ:MAX⟫ − 𝕀:1⟩⟩] λ:STEP
    = Repeat (MAX − 1) times

  Memory expiry with computed offset:
    ℳ[τ[+⟨⟨⟪σ:TTL⟫ × 𝕀:2⟩⟩]]
    = Memory expires in (TTL * 2) turns

  Conditional on computed value:
    ⟦?⟧[⟨⟨⟪σ:SCORE⟫ ≥ 𝕀:80⟩⟩] · λ:PASS · ⟦!⟧ · λ:FAIL

OPERATOR PRECEDENCE (within arithmetic expressions, high to low)
  1. ( )          Grouping
  2. ^            Exponentiation (right-associative)
  3. ×  ÷  %      Multiplication / division / modulo (left-associative)
  4. +  −         Addition / subtraction (left-associative)

TYPE RULES
  𝕀 OP 𝕀 → 𝕀     except ÷ which → 𝔽 (always float division)
  𝔽 OP 𝔽 → 𝔽
  𝕀 OP 𝔽 → 𝔽     (integer is promoted)
  % only valid on 𝕀 operands → 𝕀
  ^ with 𝕀 exponent → same type as base; with 𝔽 exponent → 𝔽

FEATURE GUARD
  Agents that did not declare ARITH in ∇CAP{} MUST respond NAK[5] to
  any transmission containing arithmetic expressions.

SECTION 31 — PIPELINE ERROR PROPAGATION SEMANTICS
════════════════════════════════════════════════════════════════════════════════
PURPOSE
  Define what happens when a stage in a ↠ pipeline emits NAK or ERR.

PIPELINE ERROR MODES
  ↠           PIPELINE:DEFAULT      Same as ↠? (skip on error)
  ↠!          PIPELINE:STRICT       On error: abort entire pipeline.
                                    Downstream stages receive no input.
                                    Originating stage's NAK[n] is returned
                                    to the pipeline initiator as NAK[10].
  ↠?          PIPELINE:SKIP         On error: pass the upstream input
                                    unchanged to the next stage.
                                    Error is logged but not propagated.
  ↠⊘          PIPELINE:NULL_SAFE    On error: pass ⊘ (null) to next stage.
                                    Stage must accept 𝕌[T|⊘] or 𝔻 input.

  The mode suffix applies to the specific ↠ edge it annotates.
  Different edges in the same pipeline may have different modes:
    ⟨A⟩ ↠! ⟨B⟩ ↠⊘ ⟨C⟩ ↠? ⟨D⟩
  A→B: abort on fail. B→C: null-safe. C→D: skip on fail.

PIPELINE ABORT BEHAVIOR (↠!)
  1. Failing stage emits NAK[n] as its output.
  2. Downstream stages are notified via ERR[10] and MUST halt.
  3. Pipeline initiator receives NAK[10] · ERR[n] (original code nested).
  4. If the pipeline had a ⇒✓{} contract, the contract is considered
     failed → NAK[4] is also appended.

DEFAULT PIPELINE MODE
  ↠ without a mode suffix defaults to ↠? (SKIP). Agents SHOULD specify
  mode explicitly on all edges to avoid relying on the default.

QUORUM JOIN ERROR BEHAVIOR
  When a fork produces N agents and JOIN has quorum ⊙[∃[𝕀:K]]:
  - If K agents respond with ACK before timeout/next turn → JOIN succeeds.
  - If fewer than K agents respond → NAK[11] · ⊙[∃[𝕀:K]] returned.
  - Late responses (after quorum met) are discarded silently.
  - Responses that are NAK do NOT count toward quorum unless the
    quorum expression includes ¬ACK modifier (see Section 13).

SECTION 32 — BROADCAST ACKNOWLEDGMENT SEMANTICS
════════════════════════════════════════════════════════════════════════════════
PURPOSE
  Define whether broadcast delivery is fire-and-forget, confirmed, or
  partial-threshold.

BROADCAST ACK MODES
  ⇝           BROADCAST:DEFAULT     Fire-and-forget. No ACK expected.
                                    Sender proceeds immediately.
  ⇝!          BROADCAST:CONFIRM     Sender MUST receive ACK from every
                                    subscribed agent before proceeding.
                                    Timeout: next-turn boundary.
                                    If any agent fails to ACK → NAK[10]
                                    with the non-responding agent listed.
  ⇝?          BROADCAST:BEST_EFFORT Sender proceeds after partial ACK.
                                    Default minimum threshold: ∃[𝕀:1].
  ⇝?[∃[𝕀:N]] BROADCAST:THRESHOLD   Custom minimum ACK count N.
                                    Example: ⇝?[∃[𝕀:2]] requires 2 ACKs.
                                    If threshold not met within turn →
                                    NAK[11] returned to sender.

RECIPIENT OBLIGATION
  ⇝  (default): no response required.
  ⇝! : recipient MUST reply ACK or NAK within the turn.
  ⇝? : recipient SHOULD reply ACK if capable; silence treated as NAK.

⇜ SUBSCRIBE BEHAVIOR
  ⇜ registers an agent to receive future ⇝ and ⇝! broadcasts from a source.
  Subscriptions persist for the session unless explicitly cancelled:
    ¬⇜ ⟨AI:SOURCE⟩    Unsubscribe from source

SECTION 33 — ∇PECS MODIFIER VOCABULARY
════════════════════════════════════════════════════════════════════════════════
PURPOSE
  ∇PECS[modifiers] appears in the transmission header to configure the
  receiver's parser and behavior before the payload arrives.

SYNTAX
  ∇PECS[MODIFIER · MODIFIER · ...]

MODIFIER TOKENS
  STRICT        Receiver must reject any malformed token with NAK[5].
                Default behavior is best-effort parsing.
  LAX           Receiver should attempt best-effort parsing of unknown
                tokens (ignore rather than NAK).
  LOG           Receiver should emit a structured log of all received
                tokens and their resolved meanings.
  ECHO          Receiver should echo the full parsed transmission back
                to the sender before executing.
  DEFER         Receiver should queue and not execute until ∇GO received.
  ATOMIC        Receiver should treat the entire transmission as a single
                atomic unit: succeed fully or fail fully (no partial exec).
  TIMEOUT[N]    Receiver should NAK[9] if unable to begin execution within
                N turns. N is 𝕀.
  COMPRESS      Receiver may respond using maximum macro/session compression
                (assume sender has full session context).
  VERBOSE       Receiver should expand all macros and types in its response
                (useful for debugging / human-readable output mode).
  AUDIT         Receiver must append ©-attribution to every clause in its
                response.

DEFER + ATOMIC INTERACTION
  When both DEFER and ATOMIC are active, the queued transmission is treated
  as a single atomic unit at execution time (when ∇GO is received).
  ∇CANCEL[ID] on a DEFER+ATOMIC transmission counts as full failure of
  the atomic unit; no partial execution occurs. No NAK is issued for a
  ∇CANCEL — cancellation is a normal control action, not an error.

EXAMPLES
  ∇PECS[STRICT · ATOMIC]      Strict parsing; all-or-nothing execution
  ∇PECS[LAX · LOG]            Lenient parsing; log all tokens
  ∇PECS[DEFER] ... ∇GO        Queue until explicitly released
  ∇PECS[DEFER · ATOMIC] ... ∇GO   Atomic deferred execution
  ∇PECS[TIMEOUT[3]]           Must start within 3 turns or NAK[9]

∇GO SYNTAX (companion to DEFER)
  ∇GO                         Release all deferred transmissions in queue
  ∇GO[ID]                     Release only the transmission with session ID
  ∇CANCEL                     Discard all deferred transmissions (no NAK)
  ∇CANCEL[ID]                 Discard one deferred transmission (no NAK)
